# STM ↔ Pi LoRa 페이로드 규격 v1.1 (Pi 구현용)

> 대상: Raspberry Pi 서버 담당자
> STM 측 구현 완료 (EVDA-46). 프레임 `version = 0x02`.
> 관련 문서: `STM1/README.md`, `docs/LORA_RF_COMPLIANCE_KR.md`

---

## 0. 세 줄 요약

1. 페이로드에 **노드 ID**가 생겼습니다 (`SENSOR:STM1:HALL01:...`)
2. `seq`가 **노드 단일 카운터**로 통일됐습니다 (홀/화재가 하나를 공유)
3. 화재 프레임에 **energy**가 붙습니다 (Qt 시각화용)

**그리고 Pi 쪽에 반드시 필요한 변경이 하나 있습니다 → §5**

---

## 1. 전송 계층 (변경 없음)

LoRa E22-900T22S(1B), **고정점(fixed-point) 모드**, 채널 30, UART 115200.

### 수신 (STM → Pi)

`/dev/serial0`에서 그냥 읽으면 됩니다. 모듈이 주소 헤더를 떼어내므로
**프레임만 도착합니다.** 추가 처리 없습니다.

### 송신 (Pi → STM) — 기존 드라이버에 없는 부분

페이로드 앞에 **목적지 3바이트**를 붙여야 합니다.

```
<ADDH> <ADDL> <CH>  +  프레임

STM1 로 보낼 때 : 00 01 1E     (주소 0x0001, 채널 30)
STM2 로 보낼 때 : 00 02 1E
```

이걸 빠뜨리면 **하행이 통째로 나가지 않습니다.** 모듈이 앞 3바이트를 주소로
해석하기 때문에, 안 붙이면 프레임의 `AA 55 02`가 주소 `0xAA55` / 채널 2로
읽힙니다.

### Pi 측 설정

```
SENSOR_LINK_MODE=lora-frame
SENSOR_UART_BAUD=115200
```

```bash
stty -F /dev/serial0 115200 raw -echo
# 모드핀: M0=GPIO23, M1=GPIO24 둘 다 LOW (일반 모드)
```

## 2. 프레임 (구조 변경 없음, version 만 0x02)

```
offset  size  field
  0      2    SOF          AA 55
  2      1    version      0x02        ← v1.0 은 0x01
  3      1    message type 0x01 = SENSOR_EVENT
  4      4    sequence     big-endian, 페이로드의 <seq> 와 동일값
  8      2    payload len  big-endian
 10      N    payload      아래 §3
10+N     2    CRC-16       big-endian
```

- CRC-16/CCITT-FALSE: init `0xFFFF`, poly `0x1021`, 반전 없음, 최종 XOR 없음
- **CRC 범위는 version(offset 2)부터 payload 마지막 byte까지**
- 페이로드에 CRLF는 **붙지 않습니다** (길이 필드가 있으므로 불필요)
- message type `0x02`(ALERT_COMMAND) / `0x03`(HEARTBEAT)은 예약만 되어 있고
  현재 사용하지 않습니다

## 3. 페이로드 문법

```
홀    SENSOR:<node>:<sensor>:<state>:<seq>
화재  FIRE:<node>:<sensor>:<state>:<seq>:<energy>
```

| 필드 | 값 | 비고 |
|---|---|---|
| `<node>` | `STM1` \| `STM2` | **v1.1 신규.** 어느 보드에서 왔는지 |
| `<sensor>` | `HALL01`~`HALL04` \| `FLAME01` | 기존과 동일 |
| `<state>` | 홀 `OCCUPIED`\|`VACANT` / 화재 `DETECTED`\|`CLEARED` | 기존과 동일 |
| `<seq>` | 부호 없는 10진수 | **v1.1 변경.** 노드 단일 카운터 → §5 |
| `<energy>` | 소수 둘째 자리 실수 | **v1.1 신규.** 화재 프레임에만 |

`<energy>`는 불꽃센서 FFT의 **1~20 Hz 대역 에너지 합**입니다. 실측 범위는
평상시 0.15~0.61, 연소 중 24~103 정도입니다.

> **판정은 STM32가 합니다.** `<energy>`는 표시용이며, Pi가 이 값으로 다시
> 판정하면 책임 소재가 둘로 갈라집니다. 화재 여부는 `<state>`만 보십시오.

### v1.0 → v1.1 대조

```
v1.0   SENSOR:HALL01:OCCUPIED:142
v1.1   SENSOR:STM1:HALL01:OCCUPIED:142
              ^^^^^ 필드 하나 증가

v1.0   FIRE:FLAME01:DETECTED:12
v1.1   FIRE:STM1:FLAME01:DETECTED:144:43.70
            ^^^^^                     ^^^^^ 앞뒤로 하나씩 증가
```

## 4. 검증용 실제 바이트

그대로 파서에 넣어 테스트하실 수 있습니다. CRC는 실제 계산값입니다.

```
SENSOR:STM1:HALL01:OCCUPIED:142      (payload 31 B / frame 43 B)
AA 55 02 01 00 00 00 8E 00 1F 53 45 4E 53 4F 52 3A 53 54 4D 31 3A 48 41
4C 4C 30 31 3A 4F 43 43 55 50 49 45 44 3A 31 34 32 EF AC

SENSOR:STM1:HALL03:VACANT:143        (payload 29 B / frame 41 B)
AA 55 02 01 00 00 00 8F 00 1D 53 45 4E 53 4F 52 3A 53 54 4D 31 3A 48 41
4C 4C 30 33 3A 56 41 43 41 4E 54 3A 31 34 33 8D 48

FIRE:STM1:FLAME01:DETECTED:144:43.70 (payload 36 B / frame 48 B)
AA 55 02 01 00 00 00 90 00 24 46 49 52 45 3A 53 54 4D 31 3A 46 4C 41 4D
45 30 31 3A 44 45 54 45 43 54 45 44 3A 31 34 34 3A 34 33 2E 37 30 52 AF
```

CRC 구현 확인용 표준 벡터: `CRC("123456789") = 0x29B1`

## 5. ★ Pi 코드 변경이 필요한 항목 — 시퀀스 초기화

**이 항목만 코드 수정이 필요합니다. 나머지는 파싱 확장입니다.**

v1.1부터 `<seq>`는 **노드당 하나의 카운터**입니다. 홀 4채널과 화재가 같은
번호를 나눠 씁니다.

```
SENSOR:STM1:HALL01:VACANT:141
SENSOR:STM1:HALL02:VACANT:142
FIRE:STM1:FLAME01:DETECTED:143:43.70    ← 화재도 같은 줄기
SENSOR:STM1:HALL03:VACANT:144
```

v1.0에서는 홀과 화재가 각각 셌기 때문에 홀 141 다음에 화재 1이 오는 일이
있었고, 단일 시퀀스로 보는 수신측 가드가 이를 역행으로 판정했습니다.
v1.1은 그 문제가 구조적으로 사라집니다.

### 대신 재부팅을 처리해야 합니다

**STM32가 재부팅하면 `seq`가 1부터 다시 시작합니다.**

현재 `ParkingSensorSequenceGuard`는 `seq <= last`인 프레임을 거부하고,
`reset()` / `clear()`를 호출하는 경로가 없습니다. 그대로 두면

> STM32 재부팅 → 새 seq(1, 2, 3…)가 전부 "과거 값"으로 거부됨
> → **해당 센서가 영구히 막힘.** 장애 지속 시간 ≈ 재부팅 전 가동 시간

이 됩니다. 이건 v1.1 때문에 생기는 문제가 아니라 **v1.0에도 이미 있는
결함**이며, v1.1로 넘어오면 반드시 드러납니다.

**필요한 규약:**

```
수신한 seq 가 직전 값보다 "크게" 감소하면 노드 재부팅으로 간주하고,
해당 노드의 시퀀스 상태를 초기화한 뒤 새 값을 받아들인다.
```

"크게"의 기준은 구현하시기 나름인데, 예를 들어 `last - seq > 1000`처럼 잡으면
단순 순서 뒤바뀜(RF 재전송 등)과 재부팅을 구분할 수 있습니다. 무선 구간에서
1000이나 되돌아가는 재정렬은 일어나지 않습니다.

## 6. 전송 주기

Pi 쪽 타임아웃/판정 로직을 잡으실 때 참고하십시오.

| 스트림 | 언제 |
|---|---|
| 홀 | 상태 변화 **즉시** + 30초 하트비트 |
| 홀 (연속 변화 시) | 채널별 **5초 쿨다운**. 그 사이 변화는 합쳐져 최신 상태 1건으로 |
| 화재 (CLEARED) | 상태 변화 즉시 + 30초 하트비트 |
| 화재 (DETECTED) | **5초마다** energy 갱신 |

- **중복은 정상입니다.** 하트비트는 상태가 그대로여도 같은 값을 다시 보냅니다.
  기존처럼 멱등 처리하시면 됩니다
- **디바운스는 STM32가 합니다.** Pi에서 재디바운스하지 마십시오 (팀 계약)
- 홀 채널이 5초 안에 여러 번 바뀌면 중간 상태는 전선에 나오지 않습니다.
  최종 상태만 옵니다 — 이건 의도된 동작입니다(전파법 duty 예산)

### 왜 연속 스트리밍을 안 하는가

LoRa는 전파법상 duty cycle 2% 제한이 있습니다. energy를 1초마다 보내면
그것만으로 예산의 81%를 씁니다. 그래서 **평상시엔 조용하고 불이 났을 때만
촘촘해지는** 구조로 잡았습니다. 현재 설계의 최악 점유는 한도의 68%입니다.

Qt에서 더 촘촘한 그래프가 필요하시면 말씀해 주십시오. 다만 그건 duty를 다시
계산해야 하는 변경입니다.

## 7. 마이그레이션

프레임 `version` 바이트로 구분하시면 **STM과 Pi를 같은 순간에 배포할 필요가
없습니다.**

```
version == 0x01  →  v1.0 파서 (노드 ID 없음, 스트림별 seq, energy 없음)
version == 0x02  →  v1.1 파서
그 외            →  드롭 + 로그
```

전환 기간에 양쪽을 다 받아두시면, STM이나 Pi 한쪽만 롤백해도 링크가 깨지지
않습니다.

## 8. 참고: 점검 도구

Pi에 `~/lora_monitor.py`를 올려뒀습니다. 프레임 디코딩 + CRC 검증 +
스트림별 유실률 통계 + 역방향 송신(고정점 헤더 포함)이 들어 있습니다.
파서를 새로 만드실 때 대조용으로 쓰시면 됩니다.

```bash
python3 ~/lora_monitor.py
```
