# STM ↔ Pi LoRa 연동 규격 v1.1

> 대상: Raspberry Pi 서버 / Qt 담당자
> STM 측 구현 완료 및 실기기 검증 완료. 프레임 `version = 0x02`.
> 관련: EVDA-46, EVDA-201 / `STM1/README.md`, `docs/LORA_RF_COMPLIANCE_KR.md`

---

## 0. 세 줄 요약

1. **노드가 둘**입니다 (STM1, STM2). 페이로드에 노드 ID가 들어갑니다
2. `seq`가 **노드당 단일 카운터**입니다 (홀·화재가 하나를 공유)
3. 하행 명령은 **목적지 노드를 골라서** 보내야 합니다

**Pi 쪽에 반드시 필요한 변경 2가지 → §5, §6**

---

## 1. 시스템 구성

| 노드 | LoRa 주소 | 홀센서 | 번호판 LED | 화재센서 |
|---|---|---|---|---|
| **STM1** | `0x0001` | `HALL01`, `HALL02` | 2개 | `FLAME01` |
| **STM2** | `0x0002` | `HALL03`, `HALL04` | 2개 | 없음 |
| **Pi** | `0x0010` | — | — | — |

**센서 ID는 노드를 가로질러 전역 고유합니다.** `HALL03`은 언제나 STM2의 것입니다. Pi의 `config/parking_slots.json`이 이미 `HALL01~04`를 고유 키로 쓰고 있어서 매핑을 바꿀 필요가 없습니다.

노드 ID는 링크 진단·재부팅 감지·**하행 목적지 결정**에 씁니다.

### 무선 설정 (양쪽 동일해야 함)

```
채널 30 (922.9 MHz) / 10 dBm / 에어레이트 62.5k / UART 115200 / 고정점 모드 / LBT on
```

## 2. 전송 계층

### 수신 (STM → Pi)

`/dev/serial0`에서 그냥 읽으면 됩니다. 모듈이 주소 헤더를 떼어내므로 **프레임만 도착합니다.**

```
SENSOR_LINK_MODE=lora-frame
SENSOR_UART_BAUD=115200
```

```bash
stty -F /dev/serial0 115200 raw -echo
# 모드핀: M0=GPIO23, M1=GPIO24 둘 다 LOW (일반 모드)
```

### 송신 (Pi → STM) — 기존 드라이버에 없는 부분

프레임 앞에 **목적지 3바이트**를 붙여야 합니다.

```
<ADDH> <ADDL> <CH>  +  프레임

STM1 로 : 00 01 1E
STM2 로 : 00 02 1E        (0x1E = 채널 30)
```

빠뜨리면 **하행이 통째로 나가지 않습니다.** 모듈이 앞 3바이트를 주소로 해석하기 때문에, 안 붙이면 프레임의 `AA 55 02`가 주소 `0xAA55` / 채널 2로 읽힙니다.

> **주의: 두 노드가 같은 채널을 듣습니다.** 목적지를 STM2로 지정해도 STM1의 모듈이 전파를 수신할 수 있습니다. STM 펌웨어가 센서 번호로 자기 담당인지 판별해 무시하므로 동작에는 문제가 없지만, **목적지 주소는 정확히 지정해 주십시오** — 나중에 노드가 늘면 그 필터가 유일한 방어선입니다.

## 3. 프레임 (구조 변경 없음, version 만 0x02)

```
offset  size  field
  0      2    SOF          AA 55
  2      1    version      0x02        ← v1.0 은 0x01
  3      1    message type 0x01 = SENSOR_EVENT / 0x02 = ALERT_COMMAND
  4      4    sequence     big-endian, 페이로드의 <seq> 와 동일값
  8      2    payload len  big-endian
 10      N    payload
10+N     2    CRC-16       big-endian
```

- CRC-16/CCITT-FALSE: init `0xFFFF`, poly `0x1021`, 반전 없음, 최종 XOR 없음
- **CRC 범위는 version(offset 2)부터 payload 마지막 byte까지**
- 페이로드에 CRLF는 **붙지 않습니다** (길이 필드가 있으므로 불필요)

---

## 4. 페이로드 문법

```
홀    SENSOR:<node>:<sensor>:<state>:<seq>
화재  FIRE:<node>:<sensor>:<state>:<seq>:<energy>
```

| 필드 | 값 |
|---|---|
| `<node>` | `STM1` \| `STM2` |
| `<sensor>` | `HALL01`~`HALL04` \| `FLAME01` |
| `<state>` | 홀 `OCCUPIED`\|`VACANT` / 화재 `DETECTED`\|`CLEARED` |
| `<seq>` | 부호 없는 10진수. **노드당 단일 카운터** → §5 |
| `<energy>` | 소수 둘째 자리 실수. 화재 프레임에만 |

실제 로그 (실기기 캡처):

```
SENSOR:STM1:HALL01:OCCUPIED:15
SENSOR:STM1:HALL01:VACANT:16
SENSOR:STM1:HALL02:OCCUPIED:17
FIRE:STM1:FLAME01:DETECTED:26:42.09
FIRE:STM1:FLAME01:DETECTED:28:102.55
FIRE:STM1:FLAME01:CLEARED:29:0.61
```

`<energy>`는 불꽃센서 FFT의 **1~20 Hz 대역 에너지 합**입니다. 실측 범위는 평상시 0.2~2.4, 연소 중 23~103입니다.

> **판정은 STM32가 합니다.** `<energy>`는 표시용이며, Pi가 이 값으로 다시 판정하면 책임 소재가 둘로 갈라집니다. 화재 여부는 `<state>`만 보십시오.

### v1.0 → v1.1 대조

```
v1.0   SENSOR:HALL01:OCCUPIED:142
v1.1   SENSOR:STM1:HALL01:OCCUPIED:142
              ^^^^^ 노드 ID

v1.0   FIRE:FLAME01:DETECTED:12
v1.1   FIRE:STM1:FLAME01:DETECTED:144:43.70
            ^^^^^                     ^^^^^ energy
```

## 5. ★ Pi 변경 (1) — 시퀀스 재부팅 처리

`<seq>`는 **노드당 하나의 카운터**입니다. 홀 2채널과 화재가 같은 번호를 나눠 씁니다.

```
SENSOR:STM1:HALL01:VACANT:23
SENSOR:STM1:HALL02:VACANT:24
FIRE:STM1:FLAME01:CLEARED:25:0.52    ← 화재도 같은 줄기
SENSOR:STM1:HALL01:VACANT:30
```

**노드마다 독립적인 카운터**이므로 `(node, seq)`로 추적하십시오. STM1의 seq와 STM2의 seq는 서로 무관합니다.

### 재부팅 처리가 필요합니다

**STM32가 재부팅하면 `seq`가 1부터 다시 시작합니다.**

현재 `ParkingSensorSequenceGuard`는 `seq <= last`인 프레임을 거부하고 `reset()` 호출 경로가 없습니다. 그대로 두면

> STM32 재부팅 → 새 seq(1, 2, 3…)가 전부 "과거 값"으로 거부됨
> → **해당 노드가 영구히 막힘.** 장애 지속 시간 ≈ 재부팅 전 가동 시간

**필요한 규약:**

```
수신한 seq 가 직전 값보다 "크게" 감소하면 노드 재부팅으로 간주하고,
해당 노드의 시퀀스 상태를 초기화한 뒤 새 값을 받아들인다.
```

기준은 예를 들어 `last - seq > 1000`이면 충분합니다. 무선 구간에서 1000이나 되돌아가는 재정렬은 일어나지 않습니다.

> 이건 v1.1 때문에 생기는 문제가 아니라 **v1.0에도 있는 결함**이며, v1.1로 넘어오면 반드시 드러납니다.

## 6. ★ Pi 변경 (2) — 프레임 버전 수용 범위

`LoRaDriver.cpp`의 `consume()`이 이렇게 되어 있습니다.

```cpp
static constexpr std::uint8_t kVersion = 0x01;
...
if (buffer_[2] != kVersion) { ++rejected_frames_; ... continue; }
```

**v1.1은 `0x02`를 보내므로 지금 상태로는 모든 프레임이 거부됩니다.**

`0x01`과 `0x02`를 모두 받도록 고치고, `LoRaFrame`에 `version` 필드를 추가해 페이로드 파서가 분기하게 하는 것을 권합니다.

`encode()`도 `kVersion`을 찍는데, **STM 쪽은 하행에서 `0x01`/`0x02`를 모두 받도록 이미 고쳤으므로** 그대로 두셔도 됩니다.

> **보낼 때는 좁게, 받을 때는 넓게.** 양쪽 다 이 원칙을 지키면 STM과 Pi를 같은 순간에 배포하지 않아도 됩니다.

## 7. 하행 명령 (Pi → STM)

```
ALERT:<sensor>:LED:<ON|OFF>:<seq>
```

```
ALERT:HALL01:LED:ON:13      → STM1 로 (목적지 00 01 1E)
ALERT:HALL03:LED:ON:14      → STM2 로 (목적지 00 02 1E)
```

**센서 번호로 목적지 노드가 정해집니다.**

| 센서 | 목적지 노드 | 고정점 헤더 |
|---|---|---|
| `HALL01`, `HALL02` | STM1 | `00 01 1E` |
| `HALL03`, `HALL04` | STM2 | `00 02 1E` |

### 페일세이프 — ACK가 없는 이유

각 LED는 **마지막 ON으로부터 5초 뒤 스스로 꺼집니다.**

- **ON 유실** → LED가 안 켜짐. 다음 명령으로 복구
- **OFF 유실** → 5초 뒤 자동으로 꺼짐

둘 다 안전한 쪽으로 실패하므로 ACK/재전송 없이 성립합니다. 대신 **ON 상태를 유지하려면 5초마다 갱신 명령을 보내야 합니다.**

> ⚠️ 갱신 주기가 duty에 잡힙니다. LED 4개를 동시에 계속 켜두면 분당 48프레임이라 Pi 쪽 duty도 확인이 필요합니다. 촬영 직전에만 잠깐 켜는 현재 정책이면 문제없습니다.

## 8. 전송 주기

| 스트림 | 언제 |
|---|---|
| 홀 | 상태 변화 **즉시** + 30초 하트비트 |
| 홀 (연속 변화 시) | 채널별 **5초 쿨다운**. 그 사이 변화는 합쳐져 최신 상태 1건으로 |
| 화재 (CLEARED) | 상태 변화 즉시 + 30초 하트비트 |
| 화재 (DETECTED) | **5초마다** energy 갱신 |

- **중복은 정상입니다.** 하트비트는 상태가 그대로여도 다시 보냅니다. 멱등 처리하십시오
- **디바운스는 STM32가 합니다.** Pi에서 재디바운스하지 마십시오 (팀 계약)
- 홀 채널이 5초 안에 여러 번 바뀌면 중간 상태는 전선에 나오지 않고 최종 상태만 옵니다 — 의도된 동작입니다(전파법 duty 예산)

## 9. 검증용 실제 바이트

그대로 파서에 넣어 테스트하실 수 있습니다. CRC는 실제 계산값입니다.

```
SENSOR:STM1:HALL01:OCCUPIED:142      (payload 31 B / frame 43 B)
AA 55 02 01 00 00 00 8E 00 1F 53 45 4E 53 4F 52 3A 53 54 4D 31 3A 48 41
4C 4C 30 31 3A 4F 43 43 55 50 49 45 44 3A 31 34 32 EF AC

SENSOR:STM1:HALL03:VACANT:143        (payload 29 B / frame 41 B)
AA 55 02 01 00 00 00 8F 00 1D 53 45 4E 53 4F 52 3A 53 54 4D 31 3A 48 41
4C 4C 30 33 3A 56 41 43 41 4E 54 3A 31 34 33 8D 48

FIRE:STM1:FLAME01:DETECTED:144:43.70 (payload 36 B / frame 48 B)
AA 55 02 01 00 00 00 90 00 24 46 49 52 45 3A 53 54 4D 31 3A 46 4C 41 4D
45 30 31 3A 44 45 54 45 43 54 45 44 3A 31 34 34 3A 34 33 2E 37 30 52 AF
```

CRC 구현 확인용 표준 벡터: `CRC("123456789") = 0x29B1`

## 10. 마이그레이션

프레임 `version` 바이트로 구분하면 **STM과 Pi를 같은 순간에 배포할 필요가 없습니다.**

```
version == 0x01  →  v1.0 파서 (노드 ID 없음, 스트림별 seq, energy 없음)
version == 0x02  →  v1.1 파서
그 외            →  드롭 + 로그
```

## 11. 점검 도구

Pi에 `~/lora_console.py`를 올려뒀습니다.

```bash
python3 ~/lora_console.py
```

- 수신 프레임 디코딩 + CRC 검증 + 노드별 색 구분
- `1`~`4` 로 해당 슬롯 LED 토글 (고정점 헤더 자동 부착)
- 종료 시 노드별 유실률·CRC 실패·재부팅 감지 리포트

**Pi 서버 구현 시 대조용으로 쓰시면 됩니다.** 고정점 헤더 부착과 재부팅 감지가 그대로 구현돼 있습니다.

## 12. 검증 상태

| 항목 | 상태 |
|---|---|
| STM1 상행 (홀 2채널 + 화재) | ✅ 실기기 확인 |
| 홀 자석 반응 / 쿨다운 | ✅ 즉시 반응, 합치기 동작 확인 |

| CRC / 유실 | ✅ 148프레임 연속 무손실 |
| **STM2 노드** | ⏳ 펌웨어 준비 중 |
| **2노드 동시 운용** | ⏳ 미검증 (반이중 충돌 확인 필요) |
