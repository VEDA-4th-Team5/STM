# 펌웨어 플래시 사용량 59% 절감

> 2026-08-27 / EVDA-46
> 대상: `STM/Core/Src/freertos.c` — 불꽃 센서 FFT 초기화

---

## 발견

FFT 는 **64포인트**만 쓰는데, 펌웨어에 **4096포인트까지의 twiddle 테이블이 전부** 링크돼 있었다.

`arm_rfft_fast_init_f32()` 가 지원하는 모든 길이를 `switch` 분기로 참조한다. 실행은 한 분기만 되지만 참조는 전부 남으므로 `--gc-sections` 로도 버려지지 않는다.

```
FFT 테이블 총합    78,936 B      (텍스트의 59.6%)
실제 필요분           608 B
낭비               78,328 B
```

## 수정

초기화 함수 대신 인스턴스를 직접 채운다. **동작은 필드 단위로 동일**하다 — 원본 함수의 `case 32U` 가 채우는 값과 같다.

```c
fft_inst.Sint         = arm_cfft_sR_f32_len32;
fft_inst.Sint.fftLen  = FFT_SIZE / 2;
fft_inst.fftLenRFFT   = FFT_SIZE;
fft_inst.pTwiddleRFFT = (float32_t *)twiddleCoef_rfft_64;
```

## 결과

FLASH = text + data

| 빌드 | 전 | 후 | 절감 |
|---|---:|---:|---:|
| `-Os` (Release) | 132,968 B | **54,416 B** | **−59.1%** |
| `-O0` (Debug) | 160,740 B | 82,108 B | −48.9% |

RAM 은 변화 없음 (bss 22,872 B). 테이블은 전부 `.rodata` 라 플래시에만 있다.

## 부품 등급

| | 최소 필요 파트 |
|---|---|
| 전 | STM32F401**RC** (256K) |
| 후 | STM32F401**RB** (128K) — 41.5% 사용 |

현재 사용 중인 **RE(512K) 기준 26% → 10.4%**. 플래시 등급 **2단계 하향 가능**.

같은 F401 라인이라 핀맵·코드 변경 없이 교체 가능하다.

## 성능 — 실측 (2026-08-28)

DWT 사이클 카운터(84MHz, 1cyc = 11.9ns)로 화재 태스크의 1초 창 처리 시간을 쟀다.
`measure/EVDA-218-before` / `-after` 두 브랜치에 동일한 계측 코드를 넣고 각각 구워 비교했다.

| 항목 | 전 | 후 |
|---|---:|---:|
| FFT 처리 (`arm_rfft_fast_f32` + `arm_cmplx_mag_f32`) | 14,706 cyc / **175 µs** | 14,702 cyc / **175 µs** |
| 창 전체 (샘플 합산 → FFT → 판정) | 18,942 cyc / **225 µs** | 18,893 cyc / **224 µs** |
| CPU 점유율 (1Hz 주기) | 0.0225 % | 0.0224 % |
| 화재 태스크 스택 여유 | 143 word (572 B) | 147 word (588 B) |
| FreeRTOS 힙 여유 | 6,552 B | 6,552 B |

**연산량은 사실상 변하지 않는다.** FFT 는 energy 텔레메트리용으로 그대로 돌고,
없앤 것은 EMA 한 줄과 비교 몇 개뿐이다. 이 표의 의미는 "개선"이 아니라
**"1초에 224 µs 만 쓰므로 설계 여유가 크다"** 는 근거다.

바뀐 것은 신뢰성 쪽이다.

| 항목 | 전 | 후 |
|---|---|---|
| 부팅 후 오검출 | **간헐 발생** (한 실행에서 60초 뒤 DETECTED 고착) | 없음 (140초+ 무검출) |
| 오검출 복구 | **불가** — baseline 동결로 구조적 고착 | 해당 없음 |
| 화재 감지 지연 | 판정 신뢰 불가 | **3초** (5창 중 3) |
| 화재 해제 지연 | 복구 안 됨 | **4초** (5창 중 1 이하) |

!! 전 버전의 오검출은 **매번 재현되지 않는다.** 주변광 조건에 따라 나기도 하고
   안 나기도 한다. 재현성이 없다는 점이 오히려 이 결함의 위험한 성질이다.

### 덤 — energy 를 판정에서 뺀 근거

같은 실측에서 라이터를 댔을 때:

```
접근 순간   energy 71.16   (점화 스파이크)
연소 중     energy  0.02   ← 주변광(0.2~1.0)보다도 낮다
이탈 순간   energy 77.95
```

센서가 포화되면 창이 평평해져 AC 성분이 사라진다. **energy 만 봤으면 연소
구간을 통째로 놓쳤다.** DC 절대 임계로 간 판단이 실측으로 뒷받침된다.

## 참고

- 수정 후에는 `-O0` 로도 128K 파트에 들어간다(62.6%). **시연 전 최적화 레벨을 바꿀 필요가 없다.**
- 이제 병목은 플래시가 아니라 **RAM(약 24KB)** 이다. 더 작은 파트로 가려면 FreeRTOS 힙(15.4KB, 실사용 약 8.7KB)을 줄여야 하는데, 스택 오버플로 시 즉시 `Error_Handler()` 무한루프라 실측 없이 건드리면 안 된다.
- `arm_rfft_fast_f32` 가 float 연산이므로 **FPU 없는 계열(G0/F1/C0)은 하한선 밖**이다.

## 발표 시 표현

> "512KB 파트를 쓰고 있었지만 실제로는 128KB 로 충분했습니다."

보드는 여전히 RE 이므로 **"절감했다"가 아니라 "양산 시 RB 로 내려갈 수 있음을 확인했다"** 가 정확한 표현이다.
