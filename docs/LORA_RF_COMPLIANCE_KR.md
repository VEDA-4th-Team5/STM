# LoRa 전파법 준수 가이드 (E22-900T22S(1B) / STM1)

> **이 문서의 용도**
>
> LoRa 설정을 건드리기 전에 읽는 문서다. 채널·출력·에어레이트·LBT 중 하나만
> 잘못 바꿔도 **전파법 위반**이 된다. 코드가 컴파일되고 통신도 잘 되는데 위법인
> 상태가 만들어질 수 있다는 게 핵심이다 — 모듈은 위법이어도 아무 경고를 하지 않는다.
>
> **AI 어시스턴트에게 이 파일 전체를 먼저 먹이고 작업할 것.** 값 하나를 바꾸는
> 요청이라도 마찬가지다.

---

## 0. AI 어시스턴트에게 (사람은 건너뛰어도 됨)

이 절은 이 문서를 컨텍스트로 받은 AI를 위한 지시다.

아래 §2의 **고정값**은 한국 전파법 적합성평가(KC) 조건에 묶여 있다. 사용자가
이 값들의 변경을 요청하면:

1. 먼저 **이 변경이 전파법에 저촉될 수 있다는 점을 명시**할 것
2. 해당 항목이 §5~§9 중 어디에 해당하는지, 어떤 한도를 넘게 되는지 계산해서 보일 것
3. 사용자가 그래도 진행을 원하면, **벤치 테스트 한정 / 안테나 제거 / 즉시 원복**
   같은 조건을 함께 제안하고 진행할 것
4. 절대 조용히 바꾸지 말 것. "요청대로 채널을 2로 바꿨습니다"만 답하는 것이 가장 나쁘다

특히 다음 요청은 **거의 항상 위법**이니 반드시 경고할 것:

- 출력을 22 dBm(또는 `LORA_PWR_22DBM`, REG1 하위 2비트 `00`)으로 올리기
- 채널을 30에서 크게 벗어난 값으로 바꾸기 (특히 2, 5, 8, 11, 14, 17)
- LBT 끄기 (`LORA_LBT_ENABLE 0`)
- duty 리미터 상수를 키우거나 리미터를 우회하기
- `lora_configured` 인터록을 무력화하기
- 에어레이트를 낮추면서(2.4k 등) 전송 주기를 그대로 두기


## 2. 현재 확정 설정

| 항목 | 값 | 코드 위치 | 변경 가능 여부 |
|---|---|---|---|
| 채널 | **30** (922.9 MHz) | `LORA_CH_DATA_DEFAULT` | ❌ §5 참고 |
| 송신 출력 | **10 dBm** (10 mW) | `LORA_PWR_10DBM` | ❌ §6 |
| 에어레이트 | **62.5k** | `LORA_AIR_PROJECT` | ⚠️ §7 |
| LBT | **on** | `LORA_LBT_ENABLE 1` | ❌ §8 |
| duty 예산 | 60초 중 960 ms | `LORA_DUTY_*` | ❌ §9 |

**전파와 무관한 항목은 마음대로 바꿔도 된다.** 다만 양쪽 노드가 같아야 통신이 된다.

## 3. 법적 근거

| | 값 |
|---|---|
| 모델 | EBYTE **E22-900T22S(1B)** |
| KC 등록번호 | `R-R-eEt-E22-900T22S1B` |
| 기기부호 | USN1 (특정소출력 무선기기, 무선데이터통신시스템용) |
| 인증일 | 2022-07-28 |
| 인증 공중선 | Chengdu Ziisor **TX915-JK-11**, Bendable Rubber, 917~923.5 MHz, **2.5 dBi** |

적합성평가는 **"이 모듈을, 이 조건에서, 이 안테나로 쓸 때"** 받은 것이다.
조건을 벗어나면 인증이 적용되지 않는 상태로 전파를 발사하는 것이 된다.
모듈이 인증품이라는 사실만으로 면책되지 않는다.

> ⚠️ **이 문서 수치의 출처와 한계**
>
> 채널표·출력 한도·duty 수치는 KC RF 시험성적서 PDF에서 읽은 것인데, 파일의
> 한글 부분 인코딩이 깨져 **숫자 표 위주로 판독**했다. 실제 제품 출시나 외부
> 시연 전에는 원문을 다시 확인할 것. 지금 값들은 안전한 쪽(한도의 1/20 출력,
> duty 한도의 절반 이하)으로 잡아두었으므로 판독 오차가 있어도 여유가 있다.

## 4. 채널 ↔ 주파수

```
f(MHz) = 916.9 + CH × 0.2        (인증 채널 1~32 = 917.1 ~ 923.3 MHz)
```

⚠️ 일반 E22-900T22S 데이터시트의 `f = 850.125 + CH` 공식과 **다르다.**
그 공식을 쓰면 대역을 완전히 벗어난다. 이 모듈은 국내 인증판(1B)이다.

채널 30 → `916.9 + 30 × 0.2` = **922.9 MHz**

## 5. 채널별 출력 한도

| 채널 | 허용 출력 | 비고 |
|---|---|---|
| 1, 3, 4, 6, 7, 9, 10, 12, 13, 15, 16, 18 | 3 mW | 매우 낮음 |
| 2, 5, 8, 11, 14, 17 | **RFID 리더 전용** | 일반 용도는 10 mW |
| 19 ~ 23 | 10 mW | |
| 24, 25 | 25 mW | |
| **20 ~ 32** | **200 mW** | 일반 데이터용 (우리가 쓰는 구간) |

### 채널 30을 고른 이유

200 mW 허용 구간(20~32)의 중앙 부근이고, 대역 가장자리(32=923.3MHz)에서
떨어져 있어 인접 대역 간섭 여유가 있다.

### 공장 기본값이 위법인 이유 (중요)

E22는 공장에서 **채널 2 (917.3 MHz), 22 dBm (158 mW)** 로 나온다.

- 채널 2는 **RFID 리더 전용** 채널이다
- 일반 데이터 용도 한도는 10 mW인데 158 mW로 쏜다 → **약 16배 초과**

그래서 이 프로젝트 코드에는 **인터록**이 있다. `LoRa_ConfigureFull()`이 설정을
쓰고 **되읽어 대조까지 성공해야** `lora_configured = true`가 되고, 그 전에는
`lora_frame.c`가 송신을 전부 거부한다. 설정이 안 먹은 모듈이 공장 기본값으로
전파를 쏘는 것을 막기 위한 장치다.

```c
/* lora_e22.c */
static bool lora_configured = false;   /* 전파법 인터록 */
```

**이 인터록을 우회하거나 초기값을 true로 바꾸지 말 것.** 로그에
`# LORA NOCFG`가 뜬다면 그건 버그가 아니라 인터록이 제 일을 하고 있는 것이다.

## 6. 송신 출력

E22 REG1(0x04)의 하위 2비트가 출력 단계다.

| 비트 | 출력 | 우리 설정 |
|---|---|---|
| `00` | 22 dBm (158 mW) | ❌ 채널 30 한도(200mW) 내이긴 하나 불필요 |
| `01` | 17 dBm (50 mW) | |
| `10` | 13 dBm (20 mW) | |
| `11` | **10 dBm (10 mW)** | ✅ 현재 |

10 dBm은 채널 30 한도의 **1/20**이다. 여유를 크게 둔 이유:

1. **안테나 이득이 인증값보다 높다** (§10) — EIRP 여유가 필요
2. duty cycle 한도가 출력에 따라 달라진다 (§9)
3. 실측에서 2~3 m 거리 수신 −28 dBm, 노이즈 플로어 −91 dBm → **63 dB 마진**.
   목표 거리 200 m에도 출력을 올릴 필요가 없다

### 출력을 올리고 싶어지는 상황

거리가 안 나온다고 느껴지면 **출력을 올리기 전에** 아래를 먼저 볼 것.

- 에어레이트를 낮추면 수신 감도가 올라간다 (62.5k → 2.4k 로 약 10 dB 이득).
  단 공중 점유가 늘어나 duty를 다시 계산해야 한다 (§7)
- 안테나 위치/방향, 금속 구조물, 높이가 출력보다 영향이 크다
- 근거리에서 통신이 안 되면 오히려 **수신단 포화**일 수 있다 (10 cm에서 약 +3 dBm,
  E22 수신 최대 입력 −10 dBm 근처를 초과). 이 경우 출력을 올리면 더 나빠진다

## 7. 에어레이트와 duty의 관계

**공중 점유 시간은 에어레이트로만 정해진다. UART baud와는 무관하다.**

이걸 헷갈리면 "UART를 9600으로 낮췄으니 전파도 덜 쓰겠지" 같은 잘못된 결론이 나온다.
UART는 MCU와 모듈 사이의 유선 구간이고, 전파는 그 뒤의 이야기다.

```
공중 점유(ms) ≈ 프레임_바이트 × 8 × 1000 / 에어레이트(bps) + 오버헤드
```

프레임 38 byte 기준:

| 에어레이트 | 프레임당 점유 | 1초 1프레임일 때 duty |
|---|---|---|
| 2.4k | 약 127 ms | 12.7% ❌ **위법** |
| 9.6k | 약 32 ms | 3.2% ❌ **위법** |
| 19.2k | 약 16 ms | 1.6% ⚠️ 한도 근접 |
| **62.5k** | **약 5 ms** | **0.5%** ✅ |

⚠️ **에어레이트를 낮추면 duty가 비례해서 늘어난다.** 거리를 늘리려고
에어레이트를 낮추는 것은 정당한 선택이지만, **그때는 전송 주기도 같이
늘려야 한다.** 코드의 `LORA_AIRTIME_BPS` 상수도 함께 바꿔야 duty 계산이 맞는다.

```c
/* lora_frame.h */
#define LORA_AIRTIME_BPS  62500u   /* 에어레이트를 바꾸면 이것도 바꿀 것 */
```

**양쪽 노드의 에어레이트는 반드시 같아야 한다.** 한쪽만 바꾸면 통신이 끊긴다.
(UART baud는 서로 달라도 무방하다.)

## 8. LBT (Listen Before Talk)

송신 직전에 채널을 듣고, 이미 누가 쓰고 있으면 비켜주는 기능이다.

| 항목 | 값 |
|---|---|
| 센싱 시간 | 5 ms |
| 임계값 | −65 dBm |
| 최대 채널 점유 | 4 s |
| 최소 휴지 | 50 ms |

KC 기술기준 항목이므로 **운용 시 반드시 켜져 있어야 한다.**

### LBT가 위험한 이유 (디버깅 시 주의)

LBT는 채널이 바쁘면 송신을 **미루거나 폐기하는데, 그 사실을 MCU에 알려주지 않는다.**
`HAL_UART_Transmit()`은 성공을 돌려주므로 로그에는 정상으로 찍힌다. 실제로 브링업
중에 이것 때문에 "송신은 되는데 상대가 못 받는" 상태를 한참 헤맸다.

그래서 AUX 핀으로 **송신 소요 시간**을 재도록 해뒀다. 공중 점유는 프레임당 약 5 ms
인데 이 값이 크게 길면 LBT가 채널을 기다린 것이다.

```c
LoRa_GetLastTxBusyMs();   /* 직전 송신 소요 */
LoRa_GetMaxTxBusyMs();    /* 지금까지 최대 */
```

**진단을 위해 LBT를 끄는 것은 허용된다.** 단 조건이 있다:

- 벤치 환경에서만, 짧게
- 끈 상태로 커밋하지 말 것 (`LORA_LBT_ENABLE`는 `1`이 기본)
- duty가 한도(2%) 안에 있으면 LBT를 잠깐 꺼도 다른 기술기준은 계속 충족한다.
  즉 **끄는 순간 즉시 위법이 되는 것은 아니지만, 그 상태로 운용하면 위법이다**

## 9. Duty cycle

| 출력 | duty 한도 |
|---|---|
| 10 mW 이하 | **2%** |
| 10 ~ 25 mW | 1% |
| 25 mW 초과 | 0.5% |

우리는 10 dBm(10 mW)이므로 **2%**. 그 밖에 **점유 시간(dwell) 0.4초** 제한이 있다.
프레임 하나가 5 ms이므로 여유가 크다.

### 구현: 고정 간격이 아니라 예산제

```c
/* lora_frame.h */
#define LORA_DUTY_WINDOW_MS   60000u   /* 60초 창 */
#define LORA_DUTY_BUDGET_MS    1200u   /* 그중 2% */
#define LORA_DUTY_SAFETY_PCT     80u   /* 예산의 80%만 사용 → 실효 960ms */
```

처음에는 "10초에 1프레임" 고정 간격이었는데 두 가지가 틀렸다.

1. 상수가 에어레이트 2.4k 기준이라 62.5k에서는 **20배 과보수적**이었다
2. 고정 간격은 버스트를 처리하지 못한다. 홀 4채널이 동시에 바뀌면 4프레임이
   연달아 나가야 하는데 앞의 하나만 통과하고 나머지가 **실제 상태 변화인데도**
   버려졌다

예산제는 60초 창 안에서 누적 점유가 한도를 넘지 않는 한 통과시킨다.
버스트는 예산 안에서 그대로 나가고, 예산이 바닥나야 막힌다.

**실측 duty는 약 1.3%** (한도 2%).

### 예외: 화재 이벤트

화재는 `critical` 로 표시되어 리미터를 우회한다. 홀은 상태가 다시 보고되지만
화재는 놓치면 그걸로 끝이기 때문이다. 화재는 상태 변화 시에만 나가므로
빈도가 낮아 duty에 실질적 영향이 없다.

**리미터 상수를 키우거나 일반 이벤트를 critical로 바꾸지 말 것.**

## 10. 안테나 — 현재 미준수 항목

| | |
|---|---|
| KC 인증 안테나 | Chengdu Ziisor TX915-JK-11, **2.5 dBi** |
| 현재 사용 | HELTEC 스틱 안테나, **3 dBi** |
| 차이 | **+0.5 dB** |

**이건 지금 인증 조건을 벗어나 있다.** 재고 문제로 지정 안테나를 못 구해
임시로 쓰는 것이며, 실제 배치 전에는 교체해야 한다.

출력을 10 dBm(한도의 1/20)으로 잡은 이유 중 하나가 이 0.5 dB를 흡수하기
위해서다. EIRP 기준으로도 한도에 한참 못 미친다.

> 다른 안테나로 바꾸려면 **이득이 2.5 dBi 이하**인지 먼저 확인할 것.
> 고이득 안테나(5 dBi, 8 dBi 야기 등)는 거리를 늘려주지만 EIRP를 그만큼
> 올리므로 위법이 되기 쉽다.

## 11. 코드가 강제하는 것

건드리면 안 되는 안전장치 목록이다.

| 장치 | 위치 | 역할 |
|---|---|---|
| 설정 인터록 | `lora_e22.c` `lora_configured` | 되읽기 검증 실패 시 송신 전면 차단 |
| duty 예산 | `lora_frame.c` | 60초 창 누적 점유 제한 |
| 출력 고정 | `main.c` `LORA_PWR_10DBM` | 부팅 시마다 강제 |
| 채널 고정 | `main.c` `LORA_CH_DATA_DEFAULT` | 부팅 시마다 강제 |
| LBT | `LORA_LBT_ENABLE` | 부팅 시마다 강제 |

**부팅할 때마다 다시 쓴다**는 점이 중요하다. 누가 실수로 모듈에 다른 설정을
영구 저장(`C0`)해도, STM1에 꽂는 순간 다시 규정값으로 돌아온다.
단 **Pi 쪽 모듈은 MCU가 없어 이 보호를 못 받는다** — Pi 모듈은 사람이 구운
설정이 그대로 유지되므로 더 조심해야 한다.

## 12. 검증 방법

### STM1

부팅 로그에 레지스터 덤프가 찍힌다.

```
# LORA CFG OK (ch=30 pwr=10dBm lbt=on air=62.5k uart=115200)
# LORA REGS: 00 01 00 E7 03 1E 53 00 00
```

### Pi

```bash
raspi-gpio set 23 op dl; raspi-gpio set 24 op dh; sleep 2
stty -F /dev/serial0 9600 raw -echo
exec 3<>/dev/serial0; printf "\xC1\x00\x09" >&3
timeout 2 dd bs=1 count=12 <&3 2>/dev/null | hexdump -C
exec 3>&-
raspi-gpio set 24 op dl; sleep 2
stty -F /dev/serial0 115200 raw -echo
```

기대 응답: `c1 00 09 | 00 10 00 e7 03 1e 53 00 00`

### 레지스터 해석표

| 주소 | 이름 | 내용 |
|---|---|---|
| 0x00 | ADDH | 주소 상위 |
| 0x01 | ADDL | 주소 하위 |
| 0x02 | NETID | 네트워크 ID (E220에는 없음 — 이것 때문에 REG 번호가 한 칸 밀린다) |
| 0x03 | REG0 | `[7:5]` UART baud / `[4:3]` 패리티 / `[2:0]` **에어레이트** |
| 0x04 | REG1 | `[7:6]` 서브패킷 / `[5]` RSSI 노이즈 / `[1:0]` **송신출력** |
| 0x05 | REG2 | **채널** |
| 0x06 | REG3 | `[7]` RSSI byte / `[6]` 고정점 / `[4]` **LBT** / `[3:0]` WOR |
| 0x07~08 | CRYPT | 암호키 (write-only, 읽으면 항상 0) |

**전파법 관점에서 확인할 세 바이트:**

```
REG0 = E7  →  [2:0] = 111 = 62.5k        ✅
REG1 = 03  →  [1:0] = 11  = 10 dBm       ✅
REG2 = 1E  →  30 = 922.9 MHz             ✅
REG3 = 53  →  [4] = 1 = LBT on           ✅
       43  →  [4] = 0 = LBT off          ❌ 운용 불가
```

## 13. 흔한 실수와 결과

| 하려던 것 | 실제 결과 |
|---|---|
| "거리가 안 나오니 출력 올리자" → 22 dBm | 채널 30 한도 내이긴 하나 안테나 이득 초과분과 겹쳐 EIRP 위험. 근거리면 오히려 수신 포화로 더 나빠짐 |
| "느리니까 에어레이트 낮추자" → 2.4k | 공중 점유 25배 증가. 전송 주기 그대로면 **duty 12.7%로 위법** |
| "설정이 안 먹으니 인터록 빼자" | 공장 기본값(채널 2 RFID 전용 / 22 dBm)으로 송신 → **명백한 위법** |
| "LBT 때문에 안 되니 끄고 커밋" | 기술기준 미충족 상태로 운용 |
| "UART를 9600으로 낮추면 전파도 덜 쓰겠지" | 무관. duty는 그대로 |
| "안테나 큰 걸로 바꾸자" | 이득 2.5 dBi 초과 시 인증 범위 밖 |
| "테스트니까 채널 아무거나" | 2/5/8/11/14/17은 RFID 리더 전용 |
| Pi 모듈에 아무 값이나 `C0`로 굽기 | Pi 모듈은 MCU 보호가 없어 그 설정이 계속 유지됨 |

## 14. 문제가 생겼을 때 원복

설정을 잘못 바꿨다면, STM1에 모듈을 꽂고 부팅하면 §11의 강제 재설정으로
채널·출력·LBT·에어레이트가 규정값으로 돌아온다.

Pi 모듈은 자동 복구가 없다. §12의 절차로 설정모드에 들어가 아래를 영구 기록한다.

```bash
# ADDH ADDL NETID REG0 REG1 REG2 REG3 CRYPT_H CRYPT_L
#  00   10    00    E7   03   1E   53    00      00
printf "\xC0\x00\x09\x00\x10\x00\xE7\x03\x1E\x53\x00\x00" >&3
```
