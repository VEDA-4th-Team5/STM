# LoRa 송신 문제 수정 내역 (2026-08-06)

"LoRa가 자꾸 안 된다" 원인 점검 결과와 수정 사항. 관련 티켓 EVDA-46.

빌드 통과 (`text 141488 / data 480 / bss 21664`). **실기 검증 완료** — 아래 §검증 결과 참고.

---

## 요약

원인은 **하드웨어가 아니라 설정값 불일치**였다. 코드 구조 자체는 문제없고,
에어레이트를 2.4k → 62.5k 로 올리는 과정에서 그에 맞춰 갱신되지 않은 상수들이 남아 있었다.

| # | 문제 | 영향 |
|---|---|---|
| 1 | 홀 프레임의 97.5% 가 duty 리미터에 버려짐 | **주 증상** |
| 2 | 리미터 상수가 옛 에어레이트(2.4k) 기준 | 20배 과보수 |
| 3 | 진단 함수 3곳이 설정모드 baud 를 안 내림 | 오진 유발 |
| 4 | `LORA_DEBUG_HEX = 1` | Pi 링크 오염 |

## 1. 홀센서 송신 정책 변경 (`freertos.c` StartTaskHallSensor)

### 문제

홀센서가 **1초마다 4채널 전부** 큐에 넣고 있었다. 유선 UART 시절엔 문제없었지만
LoRa 로 넘어오면서 duty cycle 한도에 정면으로 걸린다.

```
초당 4프레임 x 60초 = 240프레임
프레임당 공중 점유   = 약 13ms  (37byte, 62.5k, preamble 포함)
60초 누적            = 3120ms
10dBm 등급 예산      = 1200ms (2%)
                     -> 2.6배 초과
```

리미터가 10초에 1프레임만 통과시키고 있었으므로 **분당 240프레임 중 6개만 나갔다.**
Pi 입장에서는 "가끔 오다 말다" 하는 것으로 보인다.

### 수정

**변화 즉시 + 10초 주기 전체 갱신**으로 바꿨다.

- 디바운스 확정된 상태가 직전 보고값과 다르면 그 슬롯만 즉시 보낸다
- 변화가 없어도 10초마다 4채널을 갱신해 liveness 를 유지한다

```
정상 상태: 4프레임 / 10초 = 60초에 24프레임 x 13ms = 312ms   (예산 960ms 내)
```

### Pi 쪽 영향 — 없음

**프레임 규격도 문자열 포맷도 그대로다.** 같은 `SENSOR:HALL01:OCCUPIED:15` 라인,
같은 메시지 타입(0x01)이다. Pi 가 중복을 idempotent 하게 처리하므로
(`DuplicateOccupiedIgnored`) 주기만 느려진 것으로 보인다.

오히려 **변화 감지는 빨라진다.** 기존엔 상태가 바뀌어도 다음 1초 경계까지 기다렸는데,
이제는 디바운스 250ms 직후 바로 나간다.

> 다만 Pi 쪽에 "1~2초 안에 안 오면 노드 다운" 같은 타임아웃이 있으면
> 10초 갱신 주기에 맞춰 늘려야 한다. **이건 확인이 필요하다.**

## 2. duty 리미터를 고정 간격 → 예산제로 교체 (`lora_frame.c/h`)

### 문제

기존 `LORA_MIN_TX_INTERVAL_MS = 10000` 은 두 가지가 틀렸다.

**(a) 상수가 옛 에어레이트 기준이었다.**
주석에 *"에어레이트 2.4k 기준 40 byte 프레임 공중 점유 대략 150ms"* 라고 적혀 있는데,
프로젝트는 이미 `LORA_AIR_PROJECT = LORA_AIR_62K5` 로 올라가 있었다.

| | 주석 가정 (2.4k) | 실제 (62.5k) |
|---|---|---|
| 40B 프레임 공중점유 | ~150 ms | **~13 ms** |
| 필요한 최소 간격 | 7.5 초 | **0.5 초** |

에어레이트를 올려서 얻은 이득을 리미터가 통째로 상쇄하고 있었다.

**(b) 고정 간격은 버스트를 처리하지 못한다.**
홀 4채널이 동시에 바뀌면 4프레임이 연달아 나가야 하는데, 앞의 하나만 통과하고
나머지는 **실제 상태 변화인데도** 버려졌다.

### 수정

간격이 아니라 **예산**으로 바꿨다. 60초 창 안에서 누적 공중 점유가 한도를 넘지
않는 한 통과시킨다. 버스트는 예산 안에서 그대로 나가고, 예산이 바닥나야 막힌다.

```c
#define LORA_DUTY_WINDOW_MS      60000u
#define LORA_DUTY_BUDGET_MS       1200u   /* 60s 의 2% */
#define LORA_DUTY_SAFETY_PCT        80u   /* 예산의 80%만 사용 = 960ms */
#define LORA_AIRTIME_BPS         62500u
#define LORA_AIRTIME_OVERHEAD_MS     8u   /* preamble/헤더 여유 */
```

공중 점유는 `LoRaFrame_EstimateAirtimeMs()` 로 프레임 길이에서 추정한다.
올림 계산 + 고정 오버헤드 8ms 로 **안전한 쪽으로 틀리게** 잡았다.

새 조회 함수:

| 함수 | 용도 |
|---|---|
| `LoRaFrame_GetAirtimeUsedMs()` | 현재 창에서 쓴 공중 점유(ms) |
| `LoRaFrame_EstimateAirtimeMs(len)` | 프레임 길이 → 추정 공중 점유 |

### 동작이 바뀐 부분 — `critical` 우회 제거

기존에는 화재 프레임(`critical=true`)이 리미터를 **완전히 우회**했다.
연속 발생 시 duty 를 넘길 수 있었다.

예산제에서는 **화재도 예산을 넘기지 못한다.** 한도를 넘긴 송신은 화재 경보라도
위법이기 때문이다. 대신 예산 자체가 넉넉해서(60초에 960ms, 프레임 약 73개)
정상 트래픽으로는 거의 닿지 않는다.

> `critical` 인자는 시그니처에 남아 있지만 현재 무시된다.
> 우선순위 큐가 필요하다고 판단되면 그때 다시 설계하는 게 맞다.

송신이 실패하면(`TXERR`) 차감했던 예산을 되돌려준다.

## 3. 설정모드 진입 시 UART baud 미조정 (`lora_e22.c`)

### 문제

E22 설정모드 UART 는 **저장된 baud 와 무관하게 항상 9600 8N1** 이다.
그런데 이 프로젝트는 평상시 115200 으로 말한다(`LORA_UART_PROJECT`).

`LoRa_ConfigureFull()` 은 맨 앞에서 `LoRa_SetBaud(LORA_CFG_BAUD)` 를 부르며
주석까지 달아뒀는데, **다음 세 함수는 그걸 안 했다.**

- `LoRa_SelfTest()`
- `LoRa_DetectVariant()`
- `LoRa_Configure()` (3인자 구버전)

정상 설정 후 이 함수들을 부르면 로컬은 115200, 모듈 설정모드는 9600 이라
**멀쩡한 모듈이 항상 무응답**으로 나온다.

### 왜 위험했나

`LoRa_DetectVariant()` 가 이 상태로 돌면 두 조합 다 `silent` 이 나오고 이렇게 찍는다:

> `둘 다 무응답. 모드 문제가 아니다 -- 전원/배선을 볼 것.`

**멀쩡한 하드웨어를 뜯어보게 만든다.** 지그에서 E22 를 E220 으로 착각했을 때
하루를 태운 바로 그 경로다. 진단 도구가 오진을 유도하고 있었다.

`main.c` 에서는 설정 실패 분기에서만 부르므로(그땐 baud 가 9600 에 남아 있음)
마스킹돼 있었지만, 정상 설정 후 상태 확인용으로 부르면 반드시 실패했다.

### 수정

세 함수 모두 진입 시 `hlora.Init.BaudRate` 를 저장 → 9600 으로 내림 →
빠져나올 때 복구하도록 했다. 모든 반환 경로에서 복구한다.

## 4. `LORA_DEBUG_HEX` 1 → 0 (`lora_frame.h`)

원래 주석대로 *"Pi 안전하지 않다"*. USART2 는 Pi 데이터 링크인데 프레임 hex 가
거기로 쏟아지면 파서가 오염된다.

벤치에서 PuTTY 로 볼 때만 1 로 두고, 연동 시에는 0 이어야 한다. 지금은 0 으로 되돌렸다.

> 디버그 출력에 duty 예산 현황도 추가했다. 1 로 켜면 이렇게 나온다:
> `# LORA OK    37B air=312ms/960ms drop=0: AA 55 01 01 ...`

---

## 검증 결과 (실기)

```
# LORA CFG OK (ch=30 pwr=10dBm lbt=on air=62.5k uart=115200)
SENSOR:HALL01:VACANT:1
# LORA OK    34B air=13ms/960ms drop=0: AA 55 01 01 00 00 00 01 00 16 53 45 4E ...
...
# LORA OK    34B air=208ms/960ms drop=0
```

| 항목 | 예측 | 실제 |
|---|---|---|
| 프레임 크기 | 10 + 22 + 2 = 34 B | 34 B |
| 프레임당 공중 점유 | 34×8÷62500 = 4.4ms → 올림 5 + 오버헤드 8 = 13ms | 13ms |
| 예산 누적 | 13 → 26 → 39 → 52 ... | 그대로 |
| 드롭 | 0 | 0 |

`CFG OK` 는 리드백 검증까지 통과했다는 뜻이다. 채널·출력·LBT·에어레이트가 모듈에
실제로 들어간 것을 되읽어 대조한 결과이므로 조용히 틀렸을 가능성이 없다.

60초 창이 다 차면 24프레임 x 13ms = **312ms / 960ms (예산의 33%)** 로 안정된다.
수정 전 방식이었다면 같은 자리에서 3120ms, 즉 예산의 2.6배였다.

## 오늘 겪은 장애의 실제 원인 (참고)

수정 작업 도중 LoRa 가 완전 무응답이 되는 일이 두 번 있었는데, **둘 다 코드가 아니라
하드웨어였다.** 같은 증상이 또 나오면 아래를 먼저 볼 것.

1. **AUX 납땜 사고.** AUX(9번 패드)를 새로 납땜한 뒤 모듈이 죽었다. AUX 는 순수 출력이라
   연결 자체는 모듈 동작을 바꾸지 않는다 — 인두를 댄 것이 옆 패드에 영향을 준 것이다.
   1.27mm 피치에서 AUX(9) 양옆이 TXD(8)/VCC(10)이고, 세 칸 건너가 **NRST(12, low reset)** 다.
2. **핀 오삽입.** 배선을 다시 꽂는 과정에서 어긋난 것으로 보인다.
   이 보드는 `D4 = PB5`, `D5 = PB4` 로 **번호가 역전**돼 있어 M0/M1 을 뒤바꾸기 쉽다.
   그리고 **M0/M1 이 뒤바뀌면 현재 진단 루틴으로는 못 잡는다** —
   `[pins]` 출력은 MCU 쪽 핀 상태만 보고, 비트뱅잉 swap 테스트는 TXD/RXD 만 확인한다.
   M1=0/M0=1 은 WOR 모드라 설정 명령에 응답하지 않아 "전원/배선 문제"처럼 보인다.

> 참고: 오늘 이전에 "A/B 모듈 불량"으로 의심했던 건은 무효다. 그 시험은 E220 인코딩
> 버그로 모듈을 딥슬립에 넣은 상태였고, 정상 모듈이라도 무조건 실패하는 조건이었다.
> **현재까지 불량으로 확인된 모듈은 없다.**

## 남은 할 일

### 1. Pi 쪽 모듈 굽기 도구 (미구현, 다음 작업의 블로커)

Pi 에 붙는 모듈은 MCU 가 없어 스스로 설정하지 못한다. STM 보드에 잠깐 물려서
C0(영구 저장)로 구워 넘겨야 하는데, **현재 그 수단이 없다.**

- `main.c` 의 평상시 경로는 `persist=false`(C2, 휘발성) → 전원 끊으면 공장값 복귀
- 지그(`STM32_MX/STM1`)의 `LoRa_Configure()` 는 채널/출력/LBT 만 건드리고
  **에어레이트와 UART 는 안 만진다** → 62.5k 가 안 들어감

제안 설계 — `lora_e22.h` 에 스위치 추가:

```c
#define LORA_BURN_MODULE   0   /* 평상시 0 */
```

1 로 빌드하면:
- `LoRa_ConfigureFull(..., persist=true)` 로 채널/출력/LBT/에어레이트/UART 를 전부 굽고
- 되읽어 확인한 뒤
- **센서 동작으로 넘어가지 않고 그 자리에서 멈춘다**

멈추는 이유는 두 가지다. 굽기는 한 번이면 되므로 부팅마다 반복해 모듈 플래시 수명을
깎을 이유가 없고, 이 모드를 켜둔 채 잊어버리면 보드가 센서 노드로 동작하지 않아
즉시 알아차릴 수 있다.

굽고 나면 모듈을 Pi 로 옮기고 값을 0 으로 되돌려 재빌드.

### 2. 그 밖

- [ ] **`LORA_DEBUG_HEX` 를 0 으로.** 현재 1(벤치 확인용). Pi 연동 전 필수 —
      USART2 는 Pi 데이터 링크라 `# LORA` 줄이 섞이면 파서가 오염된다.
- [ ] **Pi UART 설정.** `raspi-config` 로 시리얼 콘솔 끄고 하드웨어 UART 켜기,
      `dtoverlay=disable-bt`, `/dev/serial0` 을 **115200** 으로.
      Pi 쪽 모듈은 M0/M1 을 GND 에 직결해 일반 모드 고정하면 된다.
- [ ] **원시 수신 확인.** 바이너리 프레임이라 `screen` 으로는 안 보인다.
      `stty -F /dev/serial0 115200 raw -echo && hexdump -C /dev/serial0`
- [ ] **Pi 파서 연결** 후 `parking-link-tool encode` 출력과 바이트 단위 대조.
- [ ] **Pi 타임아웃 정책 확인.** 홀 갱신이 1초 → 10초로 늘었다.
      "N초 안에 안 오면 노드 다운" 로직이 있으면 조정 필요.
- [ ] **모듈 식별용 주소 굽기.** 현재 3개 모듈 모두 주소 `0x0000` / NETID `0x00` 이라
      self test 출력만으로는 어느 모듈인지 구분이 안 된다. 오늘 그것 때문에 혼선이 있었다.
      투명전송 모드에서 주소는 통신에 영향이 없으므로 순수 라벨로 쓸 수 있다.
      (예: STM1=0x0001, STM2=0x0002, RPi=0x0010)
- [ ] **M0/M1 뒤바뀜 진단 추가 검토.** 현재 어떤 진단도 이걸 못 잡는다.
- [ ] **안테나 이득 확인.** 인증 공중선 이득 2.5dBi, 보유 스틱이 3dBi 면 적합성평가 범위 밖.
- [ ] **거리 테스트.** RSSI(REG3 bit7) 켜면 링크 마진을 dBm 으로 볼 수 있다.

### 3. 알려진 미해결 (급하지 않음)

- **Pi → STM 수신 경로 없음.** `LORA_MSG_ALERT_COMMAND(0x02)` 가 정의만 돼 있고
  받는 코드가 없다. `LoRa_Recv()` 도 아무도 부르지 않는다. 단방향이 의도면 그대로 둔다.
- **`lora_tx_buf` 공유 버퍼.** 현재는 `TaskPacketTX` 하나만 송신해서 안전하다.
  다른 태스크가 직접 `LoRaFrame_SendLine()` 을 부르게 되면 뮤텍스가 필요하다.
- **공중 점유는 계산값이다.** 실측하지 않았다. 오버헤드 8ms 는 여유를 둔 값이라
  실제보다 크게 잡혔을 가능성이 높지만(= 안전한 방향), 정확한 값이 필요하면
  스코프나 RSSI 로 재야 한다.
- **`critical` 인자가 무시된다.** 예산제로 바뀌면서 화재 프레임의 리미터 우회를 없앴다.
  우선순위 큐가 필요하다고 판단되면 그때 다시 설계할 것.
